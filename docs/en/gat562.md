# GAT562 30S Mesh Kit (nRF52840)

> Translated from the Russian original [docs/gat562.md](../gat562.md); when they differ, the original is current.

The first MeshMesh board that is not an ESP32: nRF52840 (1 MB flash, 256 KB RAM, Bluetooth) and an SX1262
with a power amplifier, a 1.3" 128×64 OLED (SSD1306, I2C), a five-way joystick, a “back”
button, a buzzer, green and blue LEDs, an L76K GNSS, powered by an 18650. PlatformIO target
`gat562_30s`, board — `boards/meshmesh_gat562_30s.json`, core variant — `variants/gat562_30s`
(from MeshCore), pins — `include/BoardPins.h`, hardware layer — `src/nrf52/HardwareGat562.cpp`.

## What is there and what is not

| Feature | GAT562 |
|---|---|
| MeshCore chats: public channel and direct messages, ACK, retries, history | yes |
| Nodes, adverts, path reset | yes |
| On-screen keyboard (EN, RU, symbols) | yes, only on this board |
| Chess with contacts on the screen | yes (64×64 board, joystick) |
| MeshCore repeater and room server modes | yes |
| Radar: BLE devices and LoRa nodes, homing | yes; no Wi-Fi |
| Bluetooth LE for the Android app (pairing with a PIN) | yes |
| USB commands (`tools/device.py`), the app over USB OTG | yes |
| Wi-Fi: access point, web page over Wi-Fi, internet client, Wi-Fi radar, CSI sensor | no: the nRF52840 has no Wi-Fi |
| Offline maps | no: no SD card |
| Klondike solitaire | only on the app's web page |
| Update over Bluetooth (DFU) | no |

The web page is the same as on the ESP32 boards, but it opens only in the Android app (over BLE
or USB): the status reports `"wifi_radio": false`, and the page hides Wi-Fi and the CSI tab and
shows help for the joystick.

## The phone was already paired with the board under MeshCore

Stock MeshCore and MeshMesh on nRF52 use the same Adafruit Bluetooth stack and the same pairing
storage area (InternalFS), and the board's Bluetooth address does not change when the firmware changes.
Android treats the board as the previously paired device and takes the list of services from its cache:
app 0.3.6-app1 reported “This is not MeshMesh: no MeshMesh BLE service”. Since 0.3.6-app2
the app clears the service cache in this case (`BluetoothGatt.refresh`) and discovers them again.
With an older app version, “Forget device” in the phone's Bluetooth settings
and a new pairing with the PIN help.

## Controls

- **←/→** — pages: home, messages, nodes, chess, radar, GPS, Bluetooth, settings, modules.
- **↑/↓** — within a page: older/newer message, previous/next node or signal,
  menu items.
- **Center** — the page's action; if there are several actions — a menu.
- **Back** — close a menu or a notification; otherwise go home. **Hold “back”** — go home.
- Home → “Write to channel…”, messages → “Write reply…”, node → “Write message…”:
  on-screen keyboard. Arrows move between keys, center enters, holding center or “Send”
  sends, “back” erases a character (on an empty draft it closes). Bottom row: case,
  layout (EN → RU → symbols), space, erase, send. Top right — how many bytes
  are left. The input language does not depend on the interface language.
- Chess: node → “Chess: invite” (random color). On the board the arrows move the cursor,
  center picks up your piece (dots show its moves), center on a square makes the move; a pawn
  promotes to a queen. “Back” puts the piece down or returns to the list of games, holding center opens the
  game menu (accept/decline an invitation, draw, resign, send again, delete).
  White pieces are drawn as outlines, black ones as solid shapes.
- Settings: sound (buzzer), language, battery, screen blanking, contrast, operating mode.
- The first 5 seconds after boot — mode selection (↑/↓ and center).

## Memory and storage

```
0x00000-0x01000  MBR                   0x26000-0xD4000  application (up to 712 KB)
0x01000-0x26000  SoftDevice S140 6.1.1 0xD4000-0xED000  MeshMesh LittleFS (100 KB)
0xED000-0xF4000  the core's InternalFS (stock MeshCore, Bluetooth keyrings)
0xF4000-...      Adafruit UF2 bootloader 0.4.5 and its settings
```

Settings (the equivalent of NVS), the MeshCore key, contacts, history (2 × 12 KB), games and the
server-mode data live in the MeshMesh LittleFS (`src/nrf52/Platform.cpp`: `Preferences` on top of
files `/prefs/<name>`, written through a temporary file and a rename). The storage is created
only on a clean area or on an empty file system and is marked with the file
`/meshmesh.fs`. If a file system of another firmware remains in the area (MeshCore companion
keeps its ExtraFS there), MeshMesh does not touch it: the key and settings are not saved and transmitting
is disabled; the home page shows “Create storage…” (it must be confirmed with a second
press); the USB command `fsformat` does the same, followed by `restart`.

The stock firmware's InternalFS is not modified, except for the Bluetooth keyrings that the Adafruit
core writes after the phone is paired.

The application runs in its own FreeRTOS task with a 16 KB stack: the core's `loop` task has 4 KB,
which is too little for JSON responses. It is built with `-O2` instead of the core's `-Ofast`: otherwise Curve25519/Ed25519
expand to 640 KB.

### Screen languages

All 15 languages (translations and the CJK and Arabic font subsets, ~130 KB) do not fit 1 MB together
with the other features. So a GAT562 image carries English and Russian, or English and one chosen
language: `tools/nrf52.py package` builds the root image (English and Russian) and one image per other
language in `lang/<code>/`. Such an image has no Russian interface strings: `tr("English","Русский")`
is a macro, the translation key is computed by the compiler, and with `MM_NO_RU` (`tools/pio_lang.py`
sets it with `MM_LANG=<code>`) the Russian string does not reach the firmware, about 10 KB. The language
images build in their own folder `.pio/build-lang`: the first one whole, each next one recompiles only
`src/I18n.cpp` (`MM_LANG_EXTRA`). The Cyrillic fonts stay: Russian messages arrive over the radio. The
root image is ~653 KB of 712; the largest, Chinese, leaves ~39 KB.

The site installs the image of the chosen language (`lang_images` in `firmware/boards.json`); the app,
updating over USB, the image with the language the board already has (`langs` in the status). The
board's “Language” menu, the web page and the USB command `lang` offer only the image's languages; if
the saved settings name a language the image lacks, the board switches to English (stored with the next
settings change). Local install: `tools/nrf52.py flash <package> --lang uk`.
ESP32 boards (16 MB) still carry every language in one image.

## Installation

Package: `python tools/package.py gat562_30s` → `artifacts/meshmesh-gat562-30s-<version>/`
(`firmware.bin`, `firmware.uf2`, `firmware-dfu.zip`, `INSTALL.txt`, `manifest.json`, `lang/<code>/`).

- **From the browser** (Chrome or Edge on a computer): the website, the GAT562 board, “Install”.
  The page talks to the board's serial bootloader over Web Serial using the same protocol as
  `adafruit-nrfutil` (`site/nrf52dfu.js`; the packets match nrfutil byte for byte). A board running MeshMesh
  enters the bootloader on a 1200-baud touch; then press “Continue” and select the port once
  more (the browser requires a separate click); a board running stock MeshCore is first put into
  the bootloader by a double RESET. Only the application is written. Hardware check without a browser:
  `python tools/nrf52_dfu_check.py artifacts/meshmesh-gat562-30s-<version>` — the same JS code
  through a TCP bridge; this way 0.3.6, 0.3.5 and 0.3.6 again were written to the board with matching hashes and
  data preserved.
- **First installation** over other firmware without a browser: press RESET twice quickly — the
  `GAT562-BOOT` drive appears; copy `firmware.uf2` onto it. Stock MeshCore 1.16 does not enter
  the bootloader on a “1200-baud touch”, so the first time the button is needed.
- **Updating MeshMesh**: `python tools/nrf52.py flash artifacts/meshmesh-gat562-30s-<version>`.
  The tool does a “1200-baud touch” — the board enters the serial DFU bootloader by itself —
  and writes `firmware-dfu.zip` via `adafruit-nrfutil`; if the UF2 drive is mounted, it copies
  `firmware.uf2`. Then it compares the hash of the running build (`status.build_sha256`) with the package.
  Only the application area is written: the MeshMesh storage and InternalFS are preserved
  (verified by comparing the raw flash before and after).
- **Backup**: `python tools/nrf52.py backup` (board in drive mode) saves
  `CURRENT.UF2` and `INFO_UF2.TXT` to `backups/gat562/` (0600, two reads are compared).
  `CURRENT.UF2` of bootloader 0.4.5 covers only 0x1000–0xEA000; the rest (0xEA000–0xF4000,
  InternalFS) is read by the MeshMesh USB command `flashread ADDR LEN` (USB only, read only):
  `python tools/nrf52_dump.py PORT 0xD4000 0xF4000 FILE`.
- To restore the previous firmware: copy the saved `CURRENT.UF2` onto the bootloader drive.

## Hardware details and open questions

- Power: the setting is the SX1262 chip power (0–22 dBm), as in MeshCore; after the amplifier
  the output is higher (the seller states 30 dBm at 22). The default is 10, as on the other boards.
  Observe local regulations.
- The manufacturer's schematic is “GAT562 30S Mesh KIT V1.1 SCH.pdf” in
  [gat-iot/GAT562-family](https://github.com/gat-iot/GAT562-family). According to it: L76K TXD → P0.15
  (0 Ω), RXD ← P0.16 (through a diode), TIMEPULSE on P0.17 is not connected (R23 NC); the
  `3V3_GPS` supply is switched by a MOSFET from IO2 = P1.02 (pin 34, HIGH — on); TXD and RXD have
  10 kΩ pull-ups to `3V3_GPS`; a BME280 is on I2C. P1.01 (pin 33) is `BEE_EN`, the buzzer (in the MeshCore variant
  it is mistakenly also named the GPS power). The firmware turns IO2 on only when GPS is enabled.
- GPS does not work on our unit, and, judging by measurements, there is no module on the line:
  with IO2 on, P0.15 with the internal pull-down reads LOW (a working L76K holds
  its TXD HIGH), with the pull-up — HIGH at any IO2 (no external pull-up to `3V3_GPS` is
  visible); there are no transitions on P0.15/P0.16/P0.17 or other free pins; on I2C only
  the screen (0x3C) responds, neither the L76K nor the BME280. The manufacturer writes “GPS 模块（内置/外接）” —
  a built-in or external module. The owner opened the case: there is no GPS module on this board
  (October 2); the BME280 does not respond on I2C either. Boards with an L76K fitted should work according to the
  schematic, but we have not tested one. USB commands for checking: `gpio N pu|pd|watch`, `gpio N 0|1`,
  `i2cscan`.
- Screen: SSD1306 controller (as in MeshCore); the image is confirmed by the owner.
- Battery: divider on AIN3 (P0.05), MeshCore formula.

## Fixed in 0.3.5: hang on the splash screen

In 0.3.4 a board with GPS disabled in the settings stopped on the “MeshMesh” splash screen at every start
(power-on, mode change): `Serial1.end()` of the Adafruit core waits forever for
UART stop events, and a UART that was never started does not produce them. Now the GPS port is stopped
only if it was started. Data was not harmed by the hang: the USB bootloader (1200-baud touch)
works even with a hung application, and a DFU update does not touch the storage.

For such cases there is a diagnostic build: `PLATFORMIO_BUILD_FLAGS=-DMM_BOOT_TRACE=1 pio run
-e gat562_30s`. It waits for a USB connection, answers
`flashread ADDR LEN` before mounting the storage (to save the storage) and starts on the command `go`, printing every
startup step (`BOOT …`). It is installed via DFU (the build's `firmware.zip`), and then the normal build is put back.

Verified on the device on October 2: restarts with GPS disabled and enabled, toggling
GPS on the fly, switching from repeater mode to normal mode; the key, history and contacts were preserved.

## Verified (October 1, 2026)

On the connected board (USB `239a:8029`, UF2 bootloader 0.4.5, S140 6.1.1); before installation — a
full flash copy (`CURRENT.UF2` + raw 0xD4000–0xF4000) and a snapshot of the stock MeshCore
v1.16.0 settings (repeater `GAT562 Repeater`, 868.731/62.5/SF8/CR6, 22 dBm):

- UF2 installation and subsequent DFU updates with matching build hashes; the area
  0xD4000–0xF4000 matches byte for byte after DFU; the boot counter and data are preserved;
- startup: LoRa SX1262, MeshCore key, storage, cryptographic self-test;
- radio with the ThinkNode M9: adverts in both directions (−37/−34 dBm), direct messages in both
  directions with the “delivered” status (ACK), one copy, Cyrillic, no restarts; reception of
  the local network's repeaters;
- chess: an invitation to the M9 and its cancellation delivered with ACK, a game survived a restart; a game with the M9
  on the GAT562 screen with the joystick was checked by the owner;
- repeater and room server modes start with the same key, return to normal mode;
  not checked from the official MeshCore app;
- BLE: pairing with a Mac with the PIN, `status` (~2 KB in notifications), `nodes`, a 238-byte command;
- radar: 16–19 BLE devices and LoRa nodes;
- screen, joystick, “back” button and buzzer — confirmed by the owner; typing and sending a
  message with the on-screen keyboard was done by him on the device;
- the web page through `tools/web_usb_bridge.py` in headless Chromium;
- Android app 0.3.4 (versionCode 3) in the emulator with the board through `tools/usb_tcp_bridge.py`
  (the same command layer as USB OTG and BLE on the phone): home, chats, nodes, BLE/LoRa radar,
  connections without Wi-Fi, modules, chess; a direct message to the M9 from the app was delivered (✓✓).

On October 2 the owner connected the Android app from the website to the board over Bluetooth on his phone
(after clearing the stale pairing from MeshCore) — it works.

Not verified: GPS (no module is fitted on our board), the app over USB OTG on a phone,
the “Create storage…” action on the device, range and power after the amplifier,
power consumption.
