# Heltec Mesh Node T114 (nRF52840)

The second nRF52840 board of MeshMesh (1 MB flash, 256 KB RAM, Bluetooth) after the GAT562: SX1262,
a 1.14" 240×135 colour TFT (ST7789), one USER button, a green LED, an L76K GNSS (in the GPS
version), a battery connector. PlatformIO target `heltec_t114`, board file
`boards/meshmesh_heltec_t114.json`, core variant `variants/heltec_t114` (from MeshCore), pins in
`include/BoardPins.h`, hardware layer `src/nrf52/HardwareT114.cpp`. Storage, Bluetooth, radar, USB
and installation are the shared nRF52 layer, as on the GAT562 ([gat562.md](gat562.md)).

## What it has and what it lacks

| Feature | T114 |
|---|---|
| MeshCore chats: public channel, channels and direct, ACK, retries, history | yes |
| Nodes, adverts, path reset | yes |
| Chess with contacts on the screen, one button | yes, a 128×128 colour board |
| MeshCore repeater and room modes | yes |
| Radar: BLE devices and LoRa nodes, homing | yes; no Wi-Fi |
| GPS (L76K), clock from GPS | yes, when the module is fitted |
| Bluetooth LE for the Android app (PIN pairing), USB commands | yes |
| Wi-Fi: access point, web page over Wi-Fi, internet, Wi-Fi radar, CSI | no: the nRF52840 has no Wi-Fi |
| Offline maps, on-screen keyboard | no (no SD card; one button) |

## Screen

The interface logic is the Heltec V4's one-button one (`src/UiHeltec.cpp`): the same pages, menus,
actions, texts and chess. On the T114 a separate layer, `src/UiHires.inc`, draws them at the native
240×135 in the style of the M9 (`src/Ui.cpp`): the M9 colours (`include/Palette.h`), the same icons
(`include/UiIcons.h`, shared with the M9), dark rounded cards, the teal bar on the chosen row, node and
channel avatars, a status bar with the title, unread, Bluetooth, GPS, signal, clock and battery (a long
title drops the battery percentage, then the Bluetooth icon), and key chips at the bottom: "click →
next screen" and "hold → action". Home is the node card with the frequency and TX/RX counters and three
tiles: chats, nodes, chess. A message shows the sender with an avatar and the text in a bubble (own ones
dark teal), a node is a card with its type, signal and distance, the radar a list coloured by signal
kind, homing the level, trend and peak.

Text: 9×15, 10×20 (bold by drawing twice, for names only: it smudges dense letters), 7×13 and inr24.
Glyphs these fonts lack (CJK, Arabic, extended Latin) are drawn at their own size from the image's 12-20
px font subsets, as tall as the 10×20 capitals.

Chess fills the screen: the 128×128 board (16×16 squares in classic colours, 12×13 piece silhouettes,
white ones outlined, yellow dots on reachable squares, a cyan cursor, the last move highlighted), and on
the right the opponent, colour, state, the chosen move in a chip, the last move and its own key chips.

The buffer is 240×135 with a byte per pixel (a palette index, 32 KB instead of 64 KB of RGB565);
`flush()` sends only the rows that changed, over SPIM3 at 32 MHz. Monochrome boards do not use this
layer; their screens are unchanged (byte-identical in `tools/ui_preview`). A USB screenshot
(`tools/device.py --screenshot`) gives 240×135 RGB565; the board converts the palette on the fly, as
64 KB in one piece cannot be allocated on the nRF52 heap. Host preview:
`tools/ui_preview/build.sh t114 OUTDIR [LANG]` (the Heltec one-button scenario with its checks).

### Pet

The "Pet" screen comes after "Chess": the creature in colour on a card (scale 5, 80×80 pixels, the body
colour by species), a speech bubble over its name, the food, joy and health bars with icons; an egg shows
the time until it hatches, a dead pet its grave. Holding the button opens the menu "Pet", "Feed", "Heal",
"Death: on/off" ("New egg" at a grave). The pet's colours are in the palette (body and accent of each of the 15 species,
`include/Palette.h`). The largest T114 language image (Chinese) with the pet leaves 8 KB of flash. On the
board (7 October) the screen, the menu and "Pet" were checked with USB keys; the button and radio reception
with the pet were not. Emulator: `tools/ui_preview/build.sh t114`; details in [pet.md](pet.md).

## Controls

As on the Heltec V4: **click** — next screen or menu item, **hold ~1.2 s** — the screen's action or its
menu. Chess: on your move a click steps through the pieces that can move, then "Game menu", hold picks
the piece; then a click steps through the squares it reaches, then "Cancel", hold plays the move. The
first 5 seconds after boot choose the device mode.

## Idle operation and power saving

With the screen off, the nRF52 application task waits for up to 20 ms instead of polling every
2 ms. A LoRa interrupt immediately notifies the task; FreeRTOS and the SoftDevice control actual
CPU sleep. Transmission/queued packets, radar and the first second after a USB/BLE command
or button input retain the fast loop. Buttons, USB and GPS are serviced between waits; LoRa
reception remains continuous. In `status`, `idle_waits`, `idle_wait_ms` and `idle_radio_events`
count waits, their elapsed time and LoRa notifications received while waiting. These do not
measure CPU sleep time or current; `sleeps`/`sleep_ms` refer to ESP32 light sleep.
RXPS and scheduled GPS power cycling are not enabled yet.
[EasySkyMesh measurements](https://github.com/IoTThinks/EasySkyMesh/wiki/PowerSaving#3-test-results)
inform the next steps; their current figures are not measurements of MeshMesh. Run
`tools/power_check.py --port PORT`; adding `--peer PORT` checks LoRa advert reception while idle.

## Memory and storage

Flash layout, SoftDevice (S140 6.1.1) and bootloader match the GAT562: application 0x26000–0xD4000,
MeshMesh LittleFS 0xD4000–0xED000, the core's InternalFS 0xED000–0xF4000, Heltec's UF2 bootloader
("HT-n5262", version 0.9.0) from 0xF4000. An image holds English, Russian and one more screen
language (`lang/<code>/`); the root image is ~634 KB of 712, Chinese is the largest. The board has a
2 MB external QSPI flash (MX25R1635F); MeshMesh does not use it yet.

USB: the firmware is 239a:8071, the bootloader 239a:0071 (as with Adafruit: the application has the
0x8000 bit). The stock Meshtastic used 239a:4405; MeshMesh does not, so the site, the app and
`tools/nrf52.py` tell firmware from bootloader the same way on every nRF52 board.

After Meshtastic or MeshCore, the area at 0xD4000 holds foreign bytes: MeshMesh leaves them, does not
save its key and keeps transmitting off until storage is created ("Modules → Create storage…" or the
USB command `fsformat`, then `restart`).

## Installation

- **From the browser** (Chrome or Edge on a computer): the website, Heltec T114, "Install" — as for
  the GAT562. A board with other firmware first goes to the bootloader by pressing RESET twice.
- **UF2 drive**: press RESET twice quickly — an `HT-n5262` drive appears; copy `firmware.uf2` onto it.
- **MeshMesh update**: `python tools/nrf52.py flash artifacts/meshmesh-heltec-t114-<version>` — the
  1200-baud touch puts the board into serial DFU, `firmware-dfu.zip` is written, the build hash is
  compared. The tool needs a backup in `backups/t114/` and checks the running board's `board` against
  the package.
- **Backup**: `python tools/nrf52.py backup` with the bootloader drive mounted — `CURRENT.UF2`
  (0x1000–0xEA000) into `backups/t114/` (by the drive's Board-ID), mode 0600.

## Pins

From the MeshCore (`heltec_t114`) and Meshtastic (`heltec_mesh_node_t114`) variants: LoRa on SPI (SCK
P0.19, MOSI P0.22, MISO P0.23, NSS P0.24, DIO1 P0.20, BUSY P0.17, RESET P0.25), 1.8 V TCXO, DIO2 as
the antenna switch. TFT on SPI1 (SCK P1.08, MOSI P1.09), CS P0.11, DC P0.12, RESET P0.02, supply
VTFT_CTRL P0.03 and backlight P0.15 (both active low, the backlight by PWM). Button P1.10, LED P1.03
(active low). Battery on AIN2 (P0.04) through a ×4.9 divider switched by P0.06. GPS: VEXT supply
P0.21, RX P1.05 ← module TX, TX P1.07 → module, RESET P1.06 (active low), STANDBY P1.02 (high = awake).
MeshCore's variant sets `SX126X_POWER_EN=37`, the same pin as GPS P1.05; MeshMesh does not drive it,
and the radio starts without it.
